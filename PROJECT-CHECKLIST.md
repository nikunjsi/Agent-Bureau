# Project checklist — the living version of §1.8 / §27 / §29

`docs/BUILD-SPEC.md` already contains a director-level exhaustive pass: §1.8 (what
"done" means), §27 (36-item risk register — what will go wrong and what we do
about it), and §29 (open questions only you can answer). That content is
frozen — it's the spec. This file is the **tracked, living version**: status
against every one of those items, updated every session, plus a parking lot
for things that come up in conversation and aren't in the spec yet.

Distinct from the other three tracking docs, on purpose:
- **`docs/BUILD-SPEC.md`** — the frozen spec. Changes only when a documented
  interface actually changes.
- **`PROGRESS.md`** — a changelog. One entry per session: what landed, what
  surprised us.
- **`CLAUDE.md`** — invariants. Rules that never change regardless of milestone.
- **`PROJECT-CHECKLIST.md`** (this file) — status. Updated whenever a risk
  gets mitigated, a milestone completes, or a new idea surfaces mid-session.

## 7. Standing rules — earned, not invented

Each of these was paid for by something that went wrong. They are gathered
here because they were previously scattered across Known Issues rows,
where a rule reads as an anecdote.

1. **A test may not re-implement the ordering, wiring or call it exists to
   verify.** If it cannot reach the production path, say so in the test
   NAME, not in a comment that reads like proof. *(M3–M6 audit: four
   mutations survived the entire suite for this one reason, and in every
   case a doc comment asserted a fidelity that was not there.)*

2. **A guard is not a guard until something on the real path calls it.**
   A passing unit test tells you the guard works *if invoked*; it tells
   you nothing about whether anything invokes it. *(M7 session 1: a tier
   floor with a green test was a lock on a door nobody walked through —
   the install path went around it entirely, and only reintroducing the
   mutation revealed it.)*

3. **An ordering assertion needs a presence assertion first.**
   `indexOf(a) < indexOf(b)` passes when `a` is absent, because a
   not-found index is smaller than any real one. *(Audit fix session: the
   first draft of the §7.4 test passed under the very mutation it existed
   to catch.)*

4. **Read Known Issues before diagnosing an environmental failure.**
   *(`ELECTRON_RUN_AS_NODE` was re-diagnosed from scratch four times
   against a row that already proposed the fix. "Worth considering" at the
   end of a known-issue entry is where a fix goes to be re-diagnosed
   indefinitely.)*

5. **Any operation that could remove the user's only way back must refuse;
   operations the user can undo need not.** *(Three instances of one
   pattern before it was named: §8.0's budget reserve holds money back so
   a limit cannot silence the Director; §11.5's circuit breaker exempts
   the Director from its stop step; and M7 session 2's `fireEmployee`
   refuses the Director outright. The distinction that makes it a rule
   rather than a blanket exemption: `pause` deliberately does NOT refuse,
   because a paused Director resumes from a button needing no model
   call.)*

6. **The same decision must not be made in two places.** Two functions
   that independently derive the same value are each individually
   testable and jointly wrong, and no test of either half can see it.
   Wherever a value is derived, ask: *is this the only place that derives
   it?* *(The M7→M4 boundary check, 2026-09-07: `hireEmployee` resolved a
   model tier and stored the id; `Supervisor.assign()` re-resolved from
   the role and overwrote it. An employee hired on `fast` spawned on the
   role's `balanced`. Both halves had passing tests asserting exactly what
   they did. Fixed by making hiring store the CHOICE and the Supervisor
   make the DECISION — one derivation, one place.)*

   The tell that a codebase has this: a **write-only column** whose writer
   and reader are different subsystems. Not every write-only field is one
   — a display field waiting for its UI is benign — but a write-only
   *decision input* means something else is deciding instead.

8. **A session that closes an audit finding updates that finding's outcome
   column in the audit report, in the same commit.** Not the changelog
   instead — the report, where the next reader of that finding will look.
   *(Three stale rows before this was written: audit #21 read "Untouched"
   for three milestones after M7 fixed it and its own code comment said so;
   the model-tier Known Issue read "open, not fixed" for a day after it was
   resolved; and the two-places row the same. A row claiming an open
   problem that is closed is worse than no row at all — standing rule 4
   sends every session to these documents before diagnosing anything, so a
   stale row costs someone a real investigation into a non-problem.)*

   The close-out sweep is therefore three documents, not two: `PROGRESS.md`
   for what happened, this file for status, and the audit report for any
   finding whose state changed.

A seventh, provisional, from M7 session 2 and not yet earned by a second
instance: **a cache keyed by the obviously-right thing may still be wrong
— prefer identity over a name.** `ProbeCache` keyed by `adapter.key`
looked correct ("version and auth are machine properties") and leaked one
adapter's result to another, because `claude-code`'s probe honours
`CLAUDE_CONFIG_DIR`. Keying by instance fixed it with no test changes,
which is how the fix was known to be right.
