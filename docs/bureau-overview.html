01The idea

You describe what you want. A Director interviews you, plans it, assigns it to a team of AI employees, supervises them, and comes back when it genuinely needs you.

02How a project runs

Six stages. You are present at every boundary — that is the product.

The rule that defines the product

Bureau is a conversation, not a launcher. The office, the task board and the terminals are all observability. Someone who only ever types in the chat box must be able to take a project from idea to finished thing.

The six ways it comes back to you

KindExample
Decision“SQLite or Postgres? Here’s the trade-off, and I’d start with SQLite.”
Approval“Push this to GitHub?” · “Raise the budget to $40?”
Review“Phase 2 is done. Here’s what works — and what I didn’t test.”
Information“What’s the API URL for your staging environment?”
Blocker“Three attempts failed. Here’s what I think is actually wrong.”
Permission“Ravi wants to run npm install express. Allow?”

Every option must state its consequence. “Option A or Option B” with no explanation is rejected by validation before it ever reaches you. If you are away, the timeout always picks the safe, reversible choice — never “proceed anyway”.

03Architecture

One Electron app. Everything on your machine. No backend anywhere.

There is no server

No accounts, no cloud database, no API of ours. The app talks to your filesystem, the agent CLIs on your machine, and whichever model provider you configured — directly. “It never leaves your machine” is only a real claim if there is nothing for it to leave to.

Two deliberate constraints

The Director cannot write code. If it could, “who changed this?” becomes ambiguous and the single-committer model breaks. Reviewers cannot write either — a reviewer that can fix what it finds stops reporting and starts silently patching, which destroys the value of the review.

Most of what looks like “AI work” in this product is plain code. That is deliberate, and it is the biggest cost lever there is.

The free-tier trap, stated honestly

Free tiers advertise big request limits — but one task is 15–40 requests, not one. A “1,000 requests/day” quota is realistically 20–40 tasks a day. The setup wizard must say this in plain words, or a new user hits a wall mid-project and concludes the product is broken.

When a limit is hit, Bureau must never look like it crashed: a per-minute limit backs off quietly, a daily limit parks the work, explains it in one sentence, and resumes automatically when the quota resets — from a saved timestamp, so it survives closing the app.

One constraint that decides the free story

The Director needs an engine that supports MCP tools and session resume — that’s how it writes briefs and plans at all. Employees have a lower bar. So if a free engine turns out not to support MCP, the honest v1 position is free employees with a paid Director — which is cheaper than it sounds, since there are many employees and only one Director. The spec says to verify this during M3 and make the wizard match reality rather than shipping a free default that can’t start.

07The office

Not decoration — a status display you can read in one second.

The rule that keeps it honest

Every visual state maps to a real system state. If a sprite is typing, a model is generating. If there’s a ?, that employee genuinely raised a question. Nothing animates for decoration — and a test enforces it. The single exception is wandering to the coffee machine after five idle minutes, which is allowed because “idle for a while” is itself real information.

08Staying in control

The realistic risks aren’t dramatic. They’re an agent doing something destructive by accident, and cost running away.

Confined

Employees can only read and write inside their own workspace. Not overridable at any setting, at any autonomy level.

Never commits

Agents write files; Bureau commits. A secret scan runs before every commit and can’t be turned off.

Budgeted

Four levels of limit, all mandatory. A circuit breaker catches loops — it steers first, then constrains, then stops.

Where we’re honest about the limits

Model provider API keys are long-lived and can’t be scoped down — no provider offers that. Bureau limits the damage, but the agent process genuinely holds a working key. Anyone claiming otherwise is describing something they haven’t built. Prompt injection is contained, not prevented. And a shell command can reach the internet regardless of network policy — so roles that don’t need the network don’t get a shell either.

09Build plan

Sixteen milestones, ~35 sessions. The order is deliberate — the boring foundations first, the beautiful part late.

Smallest useful slice

M0 → M1 → M2 → M3 → M4 → a cut-down chat → intake and brief only. About 13 sessions for: “describe a project, get properly interviewed, and receive a brief you recognise as correct.” It stops at the brief — executing tasks needs worktrees, permissions and roles too. But it validates the riskiest assumption: that the conversation is worth having. If that isn’t delightful, no amount of pixel art will save it.

Beyond the build, the risks that decide whether anyone uses it: the Director asking too many questions (capped and batched), agents reporting success on work that doesn’t run (acceptance criteria, validators, independent QA), and cost surprise (mandatory budgets, live meter, estimate before approval).

The one that matters most

An agent reporting “done” on something that doesn’t work destroys trust instantly and permanently. The defence is layered: every task must declare acceptance criteria up front, validators run before any commit, the finishing agent must state what it did not verify, and the Director checks the result against the criteria rather than taking the agent’s word.
